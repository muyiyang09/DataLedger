## 一、用一句话定位（但别用术语说）

❌ 不要这么说：「我做了一个 NL2SQL 的智能问数平台，用大模型把自然语言转成 SQL。」

✅ 这么说：「**数据仓库本身的口径是含糊的，我做的是一套让答案仍然可信、可追溯、可验证的机制。**」

## 二、为什么做这个（讲"为什么"的顺序很重要）

### 从一个具体场景切进去

某天上午 10 点，运营在群里问一句：**「上个月华东的销售额是多少？」**

这句话里有三个坑，而且**三个都不会报错**：

| 词 | 数据里的实际情况 | 不问清就出事的后果 |
|---|---|---|
| 华东 | 库里存的字符串是「华东区」 | 写 `= '华东'` 命中 0 行，安静地返回 0 |
| 销售额 | `pay_amount` / `total_amount` / 明细 `item_amount` 三个字段，互不相等 | 三者差 12%~3.6%，汇报的数字和财务对不上 |
| 上个月 | 是自然月？还是滚动 30 天？含不含取消单？ | 含取消单会虚高 **13.4%**（实测 4017.8 万） |

**后果**：系统不报错、不崩溃、界面还挺好看，运营拿着这个数去开会，
被财务对账打回来——而工程师在日志里什么都看不到。

### 所以需要的能力不是"更强的模型"

需要的是三件事：

1. **口径要写下来**（不是藏在人的脑子里）→ 语义层
2. **生成的 SQL 要被静态检查**（不是靠提示词求它别乱来）→ 三层护栏
3. **答案要能被独立验算**（不是"看着挺合理"）→ 评测集 + 判分器

### 前后对比

| | 普通 NL2SQL demo | 本项目 |
|---|---|---|
| 验收标准 | 「跑通了」「demo 能演示」 | 21 条用例、12 个口径陷阱，**每个陷阱的通过率是多少** |
| 出错方式 | 报错 → 修 | **不报错，安静地给错数** ← 这才是要抓的 |
| 可信度来源 | 演示时看起来对 | 判分器本身也被反向验证过（见第五节） |

## 三、为什么按这个顺序做（最容易被追问的地方）

**当前顺序：造数据 → 写用例 → 写判分器 → 最后才接模型。**

Stage 0（数据底座）和 Stage 1 第一步（评测框架）加起来
**5,115 行代码，其中 0 行调用大模型**。这不是没做完，是刻意排的。

### 反过来做会撞上什么

如果先接模型、先做界面：

- 提示词改一个字，准确率上下浮动 10%，但你**不知道是哪条用例变好了、哪条变差了**
- 没有标准答案 SQL，你只能靠"我看了几条，感觉还行"——这句话在面试里一秒就崩
- 到最后一个项目做完了，答不出「你的准确率是多少」

**这是绝大多数同类项目烂尾的真实原因**，不是技术不行。

## 五、面试官可能问什么（按危险程度排序）

### A. 判断题 —— 考你是不是真理解

| 追问 | 怎么答（要点，不是话术） |
|---|---|
| 「这不就是调个大模型 API 吗？」 | 承认一半：跑通版约 150 行，一下午能写。**但**：现有 5,115 行里 0 行调模型。真正的难点是"数仓口径歧义"和"怎么证明答案可信"，不是生成 SQL 那一步。 |
| 「提示词写严格点不就行了？」 | 提示词是最不可信的一层：可被诱导绕过、约束列不全、无法测试。而且它管不住"数里有歧义"这件事——提示词再严，模型也不知道"销售额"该用哪个字段。 |
| 「12 个陷阱里哪个最难防？」 | 陷阱②（一级/二级类目写错，如把「男装」拿去比 `category_l1`）和陷阱①（'华东' vs '华东区'）。**因为它们不报错，安静命中 0 行** —— 所有监控指标都是绿的。 |
| 「为什么不用现成的 Spider / BIRD 评测集？」 | 因为它们考的是 **schema 复杂度**（表多、join 深），而本项目要考的是 **业务口径歧义**。Spider 里的字段名和问题基本一一对应，填空就够了，做不出"三个候选字段都对但只有一个是对的"这种题。 |
| 「如果模型答得很好，项目还有价值吗？」 | 价值反而更清楚：模型答得越好，说明它选的字段越"看起来合理"，**而看起来合理恰好是口径错误最危险的形态**。护栏和评测不因模型变强而失效。（也承认：这个论点目前是推理，Stage 1 Step 2 拿到数字后才能证明。） |

### B. 技术细节 —— 考是不是自己写的

| 追问 | 要点 |
|---|---|
| 「只读账号为什么是唯一不可绕过的护栏？」 | 前两层（提示词、AST 检查）都在"检查"，检查就有漏。只读账号是**数据库层面物理拒绝**：即使模型生成 `DROP TABLE`，也是 PG 报错。守卫逻辑可以写错，权限不会。 |
| 「为什么用 AST 而不是正则黑名单？」 | 正则可以绕：注释、大小写、`/**/`、Unicode、函数名嵌套（`pg_catalog.dr`\|`op`）。正则只能挡你知道的写法，AST 挡的是**语义**。（这一层还没写，要如实说。） |
| 「结果集怎么比对？」 | 三种：`exact`（单值精确）、`approx`（相对误差，含"分母为 0 时就要求两边都为 0"这个边界）、`unordered_set`（多重集无序比对）。**不比 SQL 字符串**——同一问题有无数种正确写法。 |
| 「gold SQL 会不会自己就是错的？」 | **会，而且我真的踩了。** 见下一节。 |
| 「你怎么知道判分器本身是对的？」 | 见下一节。这是这个项目最值得讲的一段。 |
| 「PostgreSQL 的 numeric 除法返回什么类型？怎么比对？」 | 返回 `numeric` → Python `Decimal`。所以项目一开始就把所有数值规整成 `Decimal`，`float` 走 `str()` 中转（`Decimal(0.1)` 会变成 0.1000000000000000055，`Decimal(str(0.1))` 才是 0.1）。 |
| 「多语句怎么处理？」 | 写了词法级扫描器，正确跳过单引号、双引号、`$tag$` 美元引用、两种注释。用 `split(';')` 会把 `WHERE name = 'a;b'` 劈两半，把**正确的 SQL 判成语法错误**。 |

### C. 取舍 —— 考有没有工程判断

| 追问 | 要点 |
|---|---|
| 「值严格、格式宽松，代价是什么？」 | 代价明确：一条返回 3 列、只有第 1 列对的答案会被判通过。这是刻意的——要抓的是口径，不是输出格式。但**不能静默**：会记 warning，报告里单独列。 |
| 「排行类允许列序无关比对，会不会漏判？」 | 有风险，所以不静默：先试严格列序，只有列序无关那条路能过时才判通过，并记 `matched_under_column_permutation`。**"靠宽松规则过的"必须在报告里可见。** |
| 「tolerance 怎么定的？」 | 按业务含义定，不是拍的：比率类 0.02（口径差异远大于此），金额类 0.001，需要多步推理的（Q012 双 11 日均口径有多个合理解读）放宽到 0.10。 |
| 「为什么 `unordered_set` 要四舍五入到 4 位小数？」 | 吸收"模型把比率多保留了几位小数"这类与口径无关的差异。4 位对千万级金额近似等于精确，对 0.1642 这类比率刚好吸收展示精度。**但它不是放水**：0.1642 与 0.1643 在 4 位下仍必须判为不同。 |

### D. 失败与坑 —— 面试官最爱，也最见水平

2. **判分器有个"永远返回通过"的 bug**
3. **有两条用例我测不出可复现的结果**

## 六、三个该主动讲的故事（细节都在 `docs/METRICS-LOG.md`）

### 故事 1：我给标准答案定的判据本身错了

考的是陷阱⑩「明细金额加总 ≠ 实付金额」。初版 gold_sql 是：

```sql
SELECT (SELECT SUM(item_amount) FROM order_items)::numeric
     / (SELECT SUM(pay_amount) FROM orders WHERE order_status <> 'cancelled')
```

分子**没排除取消单**，分母排除了。算出 1.1762；两边口径对齐后是 1.0357。

**它的错法，和它正在考的那个陷阱（口径不一致）完全相同。**

更细的点：分子那半句恰恰是「忘了排除取消单」——**而这是陷阱⑥在考的东西**。
所以一条错的口径里可以同时叠着两个陷阱。

**为什么值得讲：** 它在本项目自己身上验证了项目命题——
口径不一致的 SQL 不报错，只会安静地给出一个无法解释的数。连写评测集的人都会踩。

### 故事 2：判分器有过一个"永远返回通过"的 bug

`approx` 分支里，我本该用两个变量：`matched_index`（判定命中）和
`best_gap`（记录最接近的候选）。我把 `matched_index` 也放进了"记录最优候选"那一行：

```python
if best_gap is None or gap < best_gap:
    best_gap, matched_index, best_value = gap, index, value   # ← 循环第一次就赋值
```

后果：**任何单列近似用例都会被判通过**，包括偏离 80% 的答案。

**关键点：gold 引擎永远发现不了这个 bug。** gold 和自己比，本来就该通过。
它是被单测 `test_outside_tolerance_fails`（标准答案 0.1642、模型答案 0.18、
容差 2%，却被判通过）抓出来的。

**为什么值得讲：** 它的错法正是本项目要在别人身上抓的错法——
不报错、不崩溃、安静地给出一个错的结论。判分器自己先犯了一遍。

### 故事 3：我为什么不敢只看"21/21"

gold 引擎 21/21 只证明判分器**不会误杀正确答案**。
一个永远返回"通过"的判分器同样能给出 21/21。

所以我做了反向验证（`eval/negatives.yaml`）：从 12 个陷阱各推一条
**能执行、但答案确实错**的 SQL，断言全部被判为未通过。实测 21/21 被拒，
偏离幅度 0.92% ~ 476%。

**为什么值得讲：** 这说明我知道"指标好看"和"指标可信"是两件事。

  21 用例、判分器拒绝率 21/21）。准确率、首次可执行率都还没有。

  单列成"时间敏感用例"，但没修。
