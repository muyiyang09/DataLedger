# DataLedger 设计说明

> 这份文档回答三个问题：**为什么要做**、**怎么设计的**、**现在做到哪了**。
>
> 想看具体实现：`db/schema.sql`（数据设计）、`db/seed.py`（造数）、`eval/cases.yaml`（评测集）。

---

## 一、要解决的问题

### 场景：一个普通的工作日下午

数据分析师收到群里一条消息：

> 「帮我拉一下**上个月华东**的**销售额**，要报给老板。」

他打开数据库写 SQL，然后卡住了——卡在三个地方：

**第一处：「上个月」是哪段时间？**

`order_time` 是带时分秒的 `TIMESTAMP`。写 `WHERE order_time = '2026-09-01'` 会命中 0 行，
因为它被隐式补成 `2026-09-01 00:00:00`。而写 `BETWEEN '2026-09-01' AND '2026-09-30'`
又会漏掉 9 月 30 日当天带时分秒的订单，少算一天。

**第二处：「华东」对应哪个字段？**

地区表里既有 `province`（存的是「江苏省」），也有 `region_group`（存的是「华东区」）。
用户嘴里说的是「华东」，库里存的是「华东区」。写 `region_group = '华东'` 返回 0 行——
**不报错，只是安静地给一个 0**。

**第三处：「销售额」到底是哪个数？**

订单表里有三个金额字段：`total_amount`（吊牌价合计）、`discount_amount`（优惠）、
`pay_amount`（实付）。直觉写法是 `total_amount - discount_amount`，
但它**不等于** `pay_amount`——差额来自积分抵扣和运费。

### 后果

这三处，每一处的不同选择**都能自圆其说**。但选不同的答案，最后那个数字能差 **30% 以上**。

而在本项目的数据集里，这个差距是可以量化的：

| 口径选择 | 实测结果 | 差距 |
|---|---|---|
| 不排除已取消订单 | 339,285,574 | 虚高 **40,177,835**（13.4%） |
| 用 `order_time = '2026-03-01'` 查当天 | **0 行** | 正确写法是 **201 行** |
| 用内连接算退货 | 7,967 行 | 静默丢掉 **5,289 行**（40%） |

**最要命的是：这几种错误一个都不报错。** 没有异常、没有警告，
只有一张被拿去汇报的错数。等发现的时候，会已经开完了。

### 所以这个项目的命题不是「能不能生成 SQL」

而是要回答：**当数据仓库本身存在口径歧义时，怎么让系统给出的答案可信、可追溯、可验证。**

## 二、为什么不直接「Prompt → SQL」

把建表语句塞进 Prompt，让大模型直接吐 SQL——这是最直觉的做法，也是绝大多数
Text-to-SQL demo 的做法。它有三个绕不过去的问题：

**1. 准确率不可控，且错误是静默的**
如上所述，模型给出的 SQL「语法正确、能执行、结果错」。没有任何机制能发现。

**2. 推理不可追溯**
用户问「为什么是这个数」，没人答得上来。是模型猜的，还是有依据的？

**3. 没有安全边界**
模型可能生成 `DROP TABLE`、`UPDATE`、或者不带 `LIMIT` 的全表扫描。
靠 Prompt 里写「请不要删表」来约束，等于没有约束。

所以头部厂商的 ChatBI 产品（QuickBI、Smartbi 等）都没有走纯 NL2SQL 路线，
而是转向了「语义层 + 约束层」。本项目的设计思路与此一致。

## 三、整体设计

### 数据流

```
用户提问：「上个月华东卖了多少」
   │
   ├─▶ ① 语义层       把业务词绑定到确定的字段与口径
   │                   「卖了多少」→ SUM(pay_amount)，且排除 cancelled
   │                   「华东」    → region_group = '华东区'
   │                   「上个月」  → [2026-09-01, 2026-10-01)
   │                   ★ 歧义在这里被消灭，而不是留给模型猜
   │
   ├─▶ ② Schema 检索   只召回相关的表和字段（而不是全库塞进 Prompt）
   │                   表多时，这决定了模型能不能选对表
   │
   ├─▶ ③ SQL 生成      大模型基于「已消歧的问题 + 召回的 Schema」生成 SQL
   │
   ├─▶ ④ 三层护栏      ┌ 权限层：只读数据库账号（即使生成 DROP 也执行不了）
   │                   ├ 语句层：SQL 静态检查（拒绝非 SELECT、拒绝多语句）
   │                   └ 资源层：自动注入 LIMIT、查询超时、表白名单
   │
   ├─▶ ⑤ 执行          报错？把错误信息回喂给模型，最多重试 2 次
   │
   ├─▶ ⑥ 结果校验      数量级是否合理？空结果是不是因为口径写错了？
   │
   └─▶ ⑦ 输出答案      附上口径声明：「按财务口径（实付金额，已排除已取消订单）」
```

### 四层的分工

| 层 | 解决什么 | 为什么不能省 |
|---|---|---|
| 语义层 | 同一个词不同人理解不一致 | 这是**根源**。不解决它，后面全是打补丁 |
| Schema 检索 | 表多时上下文爆炸、选错表 | 真实数仓几百张表，全塞 Prompt 既贵又不准 |
| 三层护栏 | 大模型越权操作数据库 | **权限层最关键**——它是唯一不可能被绕过的 |
| 自校验重试 | 一次生成的 SQL 不可用 | 让系统有「发现自己错了」的能力 |

**关于护栏第 1 层为什么是数据库权限**：
Prompt 约束可以被绕过（诱导、注入），字符串黑名单永远有漏网（大小写、注释、编码）。
但只要数据库账号只有 `SELECT` 权限，即使模型生成了 `DROP TABLE`，
数据库层面直接拒绝——**这一层不依赖任何「猜」，是硬的**。

## 四、关键决策：为什么第一个阶段是「造数据」，而不是「写代码」

按直觉，应该先把「问句 → SQL」跑通，再去优化。

但这个项目反过来了。原因是：

> **如果 Schema 干净无歧义，Text-to-SQL 就退化成字符串拼接，
> 一个 7B 小模型也能跑出高准确率——项目也就没有难度和故事可讲了。**

所以第一步不是写代码，而是**造一个「故意带口径歧义」的数据集**，
让「语义层 + 护栏 + 评测」成为**必需品**，而不是炫技。

`db/schema.sql` 里埋了 12 个真实数仓里最常见的口径陷阱，
每一个都在字段注释里标了 `[陷阱N]`，并与评测用例一一对应：

| # | 陷阱 | 为什么真实 |
|---|---|---|
| ① | 大区存「华东区」，用户说「华东」 | 命名规范与口语永远对不齐 |
| ② | 一级/二级两级类目 | 「服装」和「男装」在不同层级，选错不报错 |
| ③ | 成本价只在商品表 | 算毛利必须跨表 join，订单表算不出来 |
| ④ | 存生日不存年龄，3% 为 NULL | 需要换算，且 NULL 会污染分母 |
| ⑤ | 注册地 ≠ 收货地（15% 跨区） | 「华东的用户」有歧义 |
| ⑥ | 含已取消订单（12%） | 不排除则销售额系统性虚高 |
| ⑦ | 三个金额字段互不相等 | 「销售额」指哪个 |
| ⑧ | `order_time` 带时分秒 | 等值比较命中 0 行 |
| ⑨ | 「销量」有三种口径 | 订单数 / 件数 / 金额 |
| ⑩ | 明细加总 ≠ 实付（差 3.57%） | 两个口径都能算「销售额」 |
| ⑪ | 退货率口径多维 | 分母三种 × 状态三种 |
| ⑫ | `refund.item_id` 可空（40% 整单退） | 内连接静默丢一半数据 |

### 配套的第二条决策：评测先行

**先把「什么算对」定义下来，再写代码去够它。**

`eval/cases.yaml` 里每条用例都带 `gold_sql`，比对方式是
**执行两条 SQL 对比结果集**，而不是对比 SQL 字符串——因为同一个问题可以有很多种正确写法。

如果反过来做（先跑通 demo，再想怎么测），项目大概率会烂尾在
「你的准确率是多少」这个问题上。

### 过程中最有价值的一次发现

复核陷阱⑩ 时，发现 `eval/cases.yaml` 里 Q021 的 **`gold_sql` 本身是错的**——
分子没排除取消单、分母排除了，算出来 1.1762（正确值是 1.0357）。

**它的错法和它在考的陷阱（⑩ = 口径不一致）完全相同。**

这件事的价值超出修一个 bug：它把本项目的核心命题**在自己身上验证了一遍**——
口径不一致的 SQL 不报错，只会安静地给出一个无法解释的数。
同时也说明 **gold_sql 也需要被审查**：标准答案错了，整条评测链就都错了。

### Stage 1 第一步：评测框架与执行器（已完成）

| 交付物 | 内容 | 实测 |
|---|---|---|
| `app/config.py` + `app/db.py` | 配置层 + 只读连接（READ ONLY + statement_timeout） | 61 + 52 行 |
| `app/execute/result.py` | 结果规整：值统一成 Decimal、保证行可哈希 | 204 行 |
| `app/execute/runner.py` | SQL 执行器 + 词法级分号切分（正确跳过字符串/注释/美元引用） | 247 行 |
| `app/execute/grader.py` | 判分器：`exact` / `approx` / `unordered_set` | 499 行 |
| `app/engines/` | SQL 来源抽象 + gold 引擎（llm 引擎留 Step 2） | 98 行 |
| `eval/run_eval.py` | 评测入口：筛选 / 分类汇总 / 按陷阱汇总 / JSON+Markdown 报告 | 470 行 |
| `eval/negatives.yaml` + `eval/verify_grader.py` | 判分器"牙齿"验证：21 条能执行但答错的 SQL | 266 行 |
| `tests/test_grader.py` | 判分器与切分器单测 | **56 passed** |

**实测数字**

| 指标 | 值 |
|---|---|
| gold 引擎通过率 | **21/21（100%）** |
| 判分器拒绝率（21 条错误答案） | **21/21（100%）**，洞 0 |
| 单测总数 | **85 passed / 0.7s** |
| 整轮耗时 | 3.08s |
| 本步新增代码 | 2,322 行 / 11 文件，**其中 0 行调用大模型** |

**为什么必须先做这一步**

`gold 21/21` 这个数本身**没有意义**——一个永远返回"通过"的判分器也能给出 21/21。

让它变得有意义的是反向验证：`eval/negatives.yaml` 里 21 条
"能执行、但答案确实错"的 SQL（每条对应一个明确的错误成因，含 Q021 那条我自己
踩过的口径坑），必须全部被判为未通过。实测全部被拒绝。

> 这一步实际抓到了一个判分器真 bug：`approx` 分支里"记录最优候选"与"判定命中"
> 共用了同一个变量，导致**任何单列近似用例都会被判通过**（哪怕偏离 80%）。
> 它不会被 gold 引擎发现，是被单测抓住的。
> **它的错法，正是本项目要在别人身上抓的错法：不报错、安静地给出一个错的结论。**

## 六、后续阶段

| 阶段 | 做什么 | 里程碑（必须能填出数字） |
|---|---|---|
| **Stage 1** | 最小闭环：问句 → SQL → 执行 → 答案 | 首次可执行率基线（预期 40%~60%） |
| ~~Stage 1 第一步~~ | ~~评测框架 + SQL 执行器 + 判分器~~ | ✅ gold 21/21；判分器拒绝率 21/21 |
| **Stage 1 第二步** | 接 DeepSeek，跑出真实基线 | ⏳ 代码就绪（生成层 + 149 tests），待 API key |
| **Stage 2** | 三层护栏 | 危险语句拦截率 100% / 正常问题误拦率 0% |
| **Stage 3** | 语义层 + Schema 检索 | 准确率相比 Stage 1 提升多少 |
| **Stage 4** | 自校验与错误回喂重试 | 重试带来的可执行率提升 |
| **Stage 5** | 评测集扩到 300 条 + 回归门禁 | 覆盖率 / 各陷阱维度的准确率 |
| **Stage 6** | 结果解读与图表 | 端到端延迟、单次成本 |

**每个阶段结束都必须能填出「里程碑」那一列。填不出来，说明该阶段还没做完。**
