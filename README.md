# DataLedger

**AI 智能问数分析平台** — 把「上个月华东卖了多少」这类自然语言问题，变成可执行、可追溯、可验证的 SQL。

---

## 为什么需要它

一个数据分析师每天要被问几十次「上个月华东卖了多少」「服装和食品哪个退货率高」。

每次都得手写 SQL：翻表结构、想 JOIN、确认口径，十分钟过去。

把这一步交给大模型，听起来很简单——把建表语句塞进 Prompt 就行了。**但只要 Schema 里有任何一处口径歧义，模型就会给出一个"能跑通、语法没错、结果是错的"的 SQL，而且没有人会发现。**

举个真实存在的坑，也是本项目数据集里真实存在的：

```sql
-- 问题："上个月销售额是多少？"
-- 写法 A（直觉版）：
SELECT SUM(total_amount - discount_amount) FROM orders WHERE ...;
-- 写法 B（财务口径）：
SELECT SUM(pay_amount) FROM orders WHERE order_status <> 'cancelled' AND ...;
```

两条 SQL 都能正常执行、都不报错，但答案可能差 **30% 以上**——
因为订单表里有 12% 的订单是已取消的，而且 `pay_amount` 因为积分抵扣和运费，
本来就不等于 `total_amount - discount_amount`。

这类错误是"静默"的：没有异常、没有告警，只有一张业务方拿去汇报的错数。

**DataLedger 要解决的不是「让模型更聪明」，而是把口径这件事从模型手里拿走，交给工程手段兜住。**

---

## 做法

不依赖"换个更强的模型"，而是四层工程约束：

| 层 | 手段 | 解决的问题 |
|---|---|---|
| 语义层 | 业务字典固化指标口径（"销售额"= `pay_amount` 且排除 cancelled） | 同一个词不同人理解不一致 |
| Schema 检索 | 按问题召回相关表与字段，而不是全库塞 Prompt | 表多时上下文爆炸、选错表 |
| 三层护栏 | 只读账号 + SQL 静态检查 + LIMIT/超时/白名单 | 大模型生成 DROP/全表扫描 |
| 自校验重试 | 执行报错回喂、结果合理性检查、最多重试 2 次 | 一次生成的 SQL 不可用 |

其中**护栏第 1 层是数据库权限**：即使模型输出了 `DROP TABLE`，数据库层面直接拒绝，
不依赖 Prompt 约束，也不依赖字符串黑名单（后者永远可能被绕过）。

## 数据集里的 12 个口径陷阱

这份 Schema（`db/schema.sql`）不是随便建的六张表，而是**故意保留了真实数仓里最常见的口径歧义**。
如果 Schema 干净无歧义，Text-to-SQL 就退化成字符串拼接，项目也就没有技术含量可言。

| # | 陷阱 | 踩中的典型问法 |
|---|---|---|
| ① | 大区存成「华东区」，用户说「华东」 | 华东销售额 → 等值匹配返回 0 行 |
| ② | 一级/二级两级类目 | 「服装」用 l1，「男装」用 l2，选错不报错 |
| ③ | 成本价只在商品表 | 毛利率必须 JOIN，订单表算不出来 |
| ④ | 存生日不存年龄，且 3% 为 NULL | 30 岁以上用户 → 分母失真 |
| ⑤ | 注册地 ≠ 收货地（15% 订单跨区） | 「华东的用户」到底按哪个算 |
| ⑥ | 含已取消订单（12%） | 销售额不排除则系统性虚高 |
| ⑦ | 三个金额字段互不相等 | 销售额该用 total 还是 pay |
| ⑧ | `order_time` 带时分秒 | `= '2025-03-01'` 命中 0 行 |
| ⑨ | 「销量」有三种口径 | 订单数 / 件数 / 金额 |
| ⑩ | 明细金额加总 ≠ 实付 | SUM(item_amount) 与 SUM(pay_amount) 不等 |
| ⑪ | 退货率口径多维 | 分母三种 × 状态三种，且订单月 ≠ 退款月 |
| ⑫ | `refund.item_id` 可空（40% 整单退） | 内连接静默丢一半数据 |

每一项在 `db/schema.sql` 的字段注释里都标了 `[陷阱N]`，并与评测用例一一对应。

## 快速开始

### 0. 准备数据库

需要 PostgreSQL 14+（**不能用 SQLite**：SQLite 没有数据库用户概念，
"只读账号"这层护栏无法演示，而它恰恰是最有说服力的一层）。

```bash
# 启动服务（Windows 管理员 PowerShell）
Start-Service postgresql-x64-18

# 建库
createdb -h 127.0.0.1 -U postgres dataledger
```

### 1. 建表

```bash
psql -h 127.0.0.1 -U postgres -d dataledger -f db/schema.sql
```

### 2. 造数

```bash
pip install "psycopg[binary]"

# 全量（约 10 万订单，视机器性能 1~3 分钟）
python db/seed.py --dsn "postgresql://postgres:<pwd>@127.0.0.1:5432/dataledger"

# 快速验证（5% 规模）
python db/seed.py --dsn "..." --scale 0.05

# 重建表结构 + 造数 + 打印陷阱自检
python db/seed.py --dsn "..." --reset
```

造数完成后会打印一份**陷阱特征自检**，例如：

```
  陷阱⑤ 跨区收货占比            15.02%    (期望 ~15%)
  陷阱⑥ 已取消订单占比          12.03%    (期望 ~12%)
  陷阱⑪ 分品类退货率    服装: 18.11% / 食品: 4.07%
  陷阱⑫ 整单退（item_id IS NULL）占比  40.12%
```

这些数字同时也是面试时的素材：**"我的数据集里 15.02% 的订单跨区收货，
所以『华东用户』这个问法必然产生歧义"** —— 这类具体数字比"我做了个 NL2SQL"有说服力得多。

### 3. 跑测试

```bash
python -m unittest discover -s tests -v
```

## 目录结构

```
DataLedger/
├─ db/
│  ├─ schema.sql          # 六张表 + 外键 + 索引 + 12 个口径陷阱 + 只读账号 DDL
│  └─ seed.py             # 造数脚本（含陷阱特征自检）
├─ eval/                  # 评测集与评测脚本（评测先行）
├─ app/
│  ├─ sqlgen/             # 语义层 + Schema 检索 + SQL 生成
│  ├─ guard/              # 三层护栏：静态检查 / 极限值注入 / 白名单
│  └─ execute/            # 执行、错误回喂、自校验重试
├─ docs/
│  └─ METRICS-LOG.md      # 每次改动的指标前后对比（没有数字的改动不算改动）
└─ tests/
```

## 开发原则

1. **先建评测集，再写业务代码。** 没有 gold SQL 的优化都是在猜。
2. **第一个里程碑是"数字"，不是"功能"。** 能跑通但不知道准确率，等于没做完。
3. **每次改动都要记录前后对比。** 改了什么、准确率从多少涨到多少、为什么。
