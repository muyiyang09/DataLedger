# DataLedger

**AI 智能问数分析平台** — 把「上个月华东卖了多少」这类自然语言问题，变成可执行、可追溯、可验证的 SQL。

---

## 为什么需要它

一个数据分析师每天要被问几十次「上个月华东卖了多少」「服装和食品哪个退货率高」。

每次都得手写 SQL：翻表结构、想 JOIN、确认口径，十分钟过去。

把这一步交给大模型，听起来很简单——把建表语句塞进 Prompt 就行了。**但只要 Schema 里有任何一处口径歧义，模型就会给出一个"能跑通、语法没错、结果是错的"的 SQL，而且没有人会发现。**

举个真实存在的坑，也是本项目数据集里真实存在的：

```sql
-- 问题："上个月销售额是多少？"
-- 写法 A（直觉版）：
SELECT SUM(total_amount - discount_amount) FROM orders WHERE ...;
-- 写法 B（财务口径）：
SELECT SUM(pay_amount) FROM orders WHERE order_status <> 'cancelled' AND ...;
```

两条 SQL 都能正常执行、都不报错，但答案可能差 **30% 以上**——
因为订单表里有 12% 的订单是已取消的，而且 `pay_amount` 因为积分抵扣和运费，
本来就不等于 `total_amount - discount_amount`。

这类错误是"静默"的：没有异常、没有告警，只有一张业务方拿去汇报的错数。

**DataLedger 要解决的不是「让模型更聪明」，而是把口径这件事从模型手里拿走，交给工程手段兜住。**

---

## 做法

不依赖"换个更强的模型"，而是四层工程约束：

| 层 | 手段 | 解决的问题 |
|---|---|---|
| 语义层 | 业务字典固化指标口径（"销售额"= `pay_amount` 且排除 cancelled） | 同一个词不同人理解不一致 |
| Schema 检索 | 按问题召回相关表与字段，而不是全库塞 Prompt | 表多时上下文爆炸、选错表 |
| 三层护栏 | 只读账号 + SQL 静态检查 + LIMIT/超时/白名单 | 大模型生成 DROP/全表扫描 |
| 自校验重试 | 执行报错回喂、结果合理性检查、最多重试 2 次 | 一次生成的 SQL 不可用 |

其中**护栏第 1 层是数据库权限**：即使模型输出了 `DROP TABLE`，数据库层面直接拒绝，
不依赖 Prompt 约束，也不依赖字符串黑名单（后者永远可能被绕过）。

> **为什么是 PostgreSQL**：这一层靠的是数据库自身的权限系统（只读账号）。
> SQLite 没有"数据库用户"这个概念，落不了地；PostgreSQL 的 `READ ONLY` 事务、
> `statement_timeout`、以及列注释（`COMMENT ON COLUMN`）三样这里都用得上。

## 数据集里的 12 个口径陷阱

`db/schema.sql` 是一个电商数仓（6 张表），**故意保留了真实数仓里最常见的口径歧义**。
如果 Schema 干净无歧义、字段名与业务名一一对应，Text-to-SQL 就退化成字符串拼接，
评测也就量不出任何东西 —— 这份 Schema 的"脏"是刻意的，并被评测集逐项覆盖。

| # | 陷阱 | 踩中的典型问法 |
|---|---|---|
| ① | 大区存成「华东区」，用户说「华东」 | 华东销售额 → 等值匹配返回 0 行 |
| ② | 一级/二级两级类目 | 「服装」用 l1，「男装」用 l2，选错不报错 |
| ③ | 成本价只在商品表 | 毛利率必须 JOIN，订单表算不出来 |
| ④ | 存生日不存年龄，且 3% 为 NULL | 30 岁以上用户 → 分母失真 |
| ⑤ | 注册地 ≠ 收货地（15% 订单跨区） | 「华东的用户」到底按哪个算 |
| ⑥ | 含已取消订单（12%） | 销售额不排除则系统性虚高 |
| ⑦ | 三个金额字段互不相等 | 销售额该用 total 还是 pay |
| ⑧ | `order_time` 带时分秒 | `= '2025-03-01'` 命中 0 行 |
| ⑨ | 「销量」有三种口径 | 订单数 / 件数 / 金额 |
| ⑩ | 明细金额加总 ≠ 实付 | SUM(item_amount) 与 SUM(pay_amount) 不等 |
| ⑪ | 退货率口径多维 | 分母三种 × 状态三种，且订单月 ≠ 退款月 |
| ⑫ | `refund.item_id` 可空（40% 整单退） | 内连接静默丢一半数据 |

每一项在 `db/schema.sql` 的字段注释里都标了 `[陷阱N]`，并与评测用例一一对应。

## 快速开始

### 0. 准备数据库

需要 PostgreSQL 14+，并确保 `psql` / `createdb` 在 PATH 里。

```bash
# 启动 PostgreSQL 服务（按你的安装方式启动即可）
#   Windows:  Start-Service <服务名>      例如 postgresql-x64-18
#   macOS:    brew services start postgresql
#   Linux:    sudo systemctl start postgresql

# 建库
createdb -h 127.0.0.1 -U postgres dataledger
```

### 1. 建表

```bash
psql -h 127.0.0.1 -U postgres -d dataledger -f db/schema.sql
```

### 2. 造数

```bash
pip install "psycopg[binary]"

# 全量（约 10 万订单，视机器性能 1~3 分钟）
python db/seed.py --dsn "postgresql://postgres:<pwd>@127.0.0.1:5432/dataledger"

# 快速验证（5% 规模）
python db/seed.py --dsn "..." --scale 0.05

# 重建表结构 + 造数 + 打印陷阱自检
python db/seed.py --dsn "..." --reset
```

造数完成后会打印一份**陷阱特征自检**（实测输出）：

```
  ① 大区命名不一致                        0.00    (等值 '华东' 命中 0 行)
  ⑤ 跨区收货占比                         14.79    (期望 ~15%)
  ⑥ 已取消订单占比                        12.05    (期望 ~12%)
  ⑥b 排除 cancelled 前后的销售额     33928.6 万 vs 29910.8 万
  ⑦ pay_amount ≠ total - discount 占比   99.88
  ⑩ 明细金额 / 实付金额 比值               1.0357
  ⑪ 退货率（按订单，仅 approved）           10.68
  ⑪b 分品类退货率    服装 16.42% / 家居 9.55% / 数码 8.56% / 美妆 7.75% / 食品 7.00%
  ⑫ 整单退（item_id IS NULL）占比          39.90
  ⑫b 内连接 vs 左连接 退货行数          7967 vs 13256
  ④ 生日为 NULL 的客户占比                  3.14
  ⑧ 时间边界：等值 vs 区间匹配             0 vs 201
  ⑨ 类目价差（服装 vs 食品）        456.7 元 vs 103.2 元
  ③ 毛利率（必须 join 商品表）             17.09
```

**三个最能说明问题的数字：**

| 输出 | 含义 |
|---|---|
| `33928.6 万 vs 29910.8 万` | 不排除已取消订单，销售额虚高 **4017.8 万**（13.4%） |
| `0 vs 201` | `order_time = '2026-03-01'` 命中 **0 行**，正确写法命中 **201 行** |
| `7967 vs 13256` | 用内连接算退货，静默丢掉 **5289 行（40%）** |

### 3. 跑评测

```bash
# ① 自检：用标准答案当"模型答案"跑一遍。必须满 21/21。
python eval/run_eval.py --engine gold

# ② 验证判分器"有牙齿"：21 条能执行但答错的 SQL，必须全部被判为未通过
python eval/verify_grader.py

# ③ 让大模型来写 SQL，拿真实基线（需要先在 .env 里配 DEEPSEEK_API_KEY）
python eval/run_eval.py --engine llm --schema-mode raw
```

`--schema-mode` 控制给模型的 schema 详略，**这三档的差值就是"把口径写下来"的价值**：

| 档位 | 给模型看什么 | 对应现实 |
|---|---|---|
| `raw` | 只有表名/列名/类型 | 朴素 NL2SQL，诚实基线 |
| `comments` | 再加列注释（含 `[陷阱N]` 的整条丢弃，见下） | 字段文档写得还行的库 |
| `full` | 再加每张表行数 | 有基本运维文档的库 |

> `comments` 档为什么要把含标记的注释**整条**丢掉：本项目 schema 的注释里，
> `[陷阱①]` 后面跟的就是答案解析（"等值匹配会返回 0 行，必须走语义层归一"）。
> 原样喂给模型等于抄答案。而**真实世界的注释也不会写"这里是坑"** ——
> 这件事同时说明：语义层必须单独做，不能拿调试笔记当口径定义。

`run_eval.py` 还支持 `--only Q001,Q017` / `--category 比率统计` / `--trap 10` 筛选，
并在 `eval/reports/` 下同时落 JSON 与 Markdown 报告（含按分类、按检查方式、
**按陷阱**的通过率分解，以及 `llm` 引擎下的 token / 成本 / P50·P95 延迟）。
`--fail-under 0.9` 可作为 CI 门禁。

**退出码约定**：`0` 正常 ｜ `1` 未达 `--fail-under` ｜ `2` 评测框架自身有问题或引擎未就绪
（第 2 种意味着"这一轮数字不可信"，CI 里必须当硬失败）。

### 4. 跑测试

```bash
python -m unittest discover -s tests -v
```

三组，共 149 个，都不依赖数据库和网络：

| 组 | 数量 | 验证什么 |
|---|---|---|
| 造数逻辑 | 29 | 12 个陷阱是否真的被造出来（否则后面的评测数字全是空的） |
| 判分器与 SQL 切分 | 56 | 每条判定决策配正反两个用例 —— 能放行对的，也能拒绝错的 |
| SQL 生成层 | 64 | 模型输出解析、schema 卡片三档、配置与错误路径 |

## 开发原则

1. **先建评测集，再写业务代码。** 没有 gold SQL 的优化都是在猜。
2. **第一个里程碑是"数字"，不是"功能"。** 能跑通但不知道准确率，等于没做完。
3. **每次改动都要记录前后对比。** 改了什么、准确率从多少涨到多少、为什么。
